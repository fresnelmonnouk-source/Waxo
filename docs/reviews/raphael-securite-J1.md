## 🔴 CRITIQUE — bloquant

### R1. Un visiteur anonyme peut vider tout le stock de la boutique en une requête, et le COD ne l'expire jamais
- **Fichiers** : `supabase/migrations/0001_core.sql:385-418` (boucle de réservation), `:390` (borne qty = 99 sans lien avec le stock), `:473-484` (`expire_stale_orders`), `:478` (`pay <> 'cod'`) ; `src/lib/checkout/schema.ts:16-20` (qty ≤ 99, ≤ 50 lignes) ; `src/lib/checkout/schema.ts:67-72` et `src/app/api/checkout/route.ts:47,63` (seules défenses : rate-limit mémoire + honeypot).
- **Confiance** : 8/10 · **VERIFIED** (traçage du code) · empreinte `0001_core.sql:397:security`
- **Code en cause** :
  - `update public.products set stock = stock - l.qty, sold = sold + l.qty where id = l.id and stock >= l.qty;`
  - `where status = 'nouvelle' and paid = false and pay <> 'cod'`
- **Scénario d'exploit** : un script envoie un seul `POST /api/checkout` avec une ligne par produit (24 produits du seed), `qty` = stock courant de chacun (`GET /api/checkout/config?ids=…` renvoie le stock publiquement), `pay: "cod"`, `website: ""`, `t: Date.now() - 3000`, et un nom/téléphone bidon. `place_order` accepte, décrémente le stock de TOUT le catalogue et retourne 200. Toute la boutique affiche « épuisé ». Comme `expire_stale_orders` exclut le COD, rien ne libère jamais ce stock : seul un admin qui remarque et annule à la main le rétablit, et l'attaquant recommence. Variante « fantôme » : commandes COD au nom/téléphone d'un tiers (livreur envoyé, ex-client harcelé), et gonflement du compteur `sold` (qui pilote le tri « populaire »). Les commandes en ligne (momo/carte) subissent la même attaque mais se libèrent après 60 min, à condition que le cron d'expiration soit réellement planifié en J3 (aujourd'hui rien ne l'appelle).
- **Correctif recommandé** (dans `place_order`, SQL, puis refléter dans `errors.ts`) :
  1. Plafonner la quantité par ligne et par commande : `l.qty > 10` → `invalid_qty` ; total d'unités de la commande (somme des `qty` + contenu des packs) ≤ 20 ; et jamais plus de 50 % du stock restant sur un seul article pour un invité.
  2. Plafond de commandes ouvertes par contact : avant l'`insert into orders`, compter `status = 'nouvelle' and not paid and created_at > now() - interval '24 hours' and (phone = <norm> or email = <email>)` ; si ≥ 3 → `raise exception 'too_many_open_orders'` et mapper vers `rate_limited` (429).
  3. Faire expirer le COD non confirmé : dans `expire_stale_orders`, ajouter la branche `(pay = 'cod' and cod_verified = false and created_at < now() - make_interval(hours => 48))`, et faire confirmer chaque COD par appel/WhatsApp avant préparation (le champ `cod_verified` existe déjà).
  4. Remplacer le rate-limit mémoire par un compteur persistant (voir O2). Planifier le cron `expire_stale_orders` dès que possible (toutes les 10-15 min) et le noter dans le brief J3.
- **Variantes (grep)** : même absence de plafond sur les `pack` (lignes 402-413) ; aucune autre route n'appelle `place_order`.

## 🟠 IMPORTANTES

### O1. Le cookie `wx_recovery` est forgeable : il permet de changer le mot de passe sans connaître l'actuel
- **Fichiers** : `src/app/api/auth/callback/[lang]/[kind]/route.ts:31` (pose du cookie), `src/app/api/me/password/route.ts:28-29,32` (contrôle), `src/lib/auth/recovery.ts:2`.
- **Confiance** : 9/10 · **VERIFIED** · empreinte `me/password/route.ts:28:security`
- **Code en cause** : `store.set(RECOVERY_COOKIE, data.user.id, { httpOnly: true, … })` et `const viaRecovery = recovery === true && store.get(RECOVERY_COOKIE)?.value === ctx.userId;`
- **Scénario d'exploit** : la valeur du cookie est l'identifiant de l'utilisateur, et `GET /api/me` renvoie cet identifiant (`id`) à son porteur de session. Quelqu'un qui détient une session ouverte (poste partagé ou cybercafé non déconnecté, jeton volé, téléphone prêté) lit son `id` via `/api/me`, ajoute à la main un cookie `wx_recovery=<id>` (httpOnly n'empêche pas de l'envoyer depuis un client HTTP ou les outils du navigateur) et appelle `POST /api/me/password {"next":"…","recovery":true}`. Le contrôle de l'ancien mot de passe, censé arrêter précisément ce cas, est sauté : le mot de passe est changé et le compte est pris durablement.
- **Correctif** : ne plus utiliser l'id comme preuve. Option A (simple) : cookie signé `userId.exp.HMAC_SHA256(secret_serveur, userId|exp)`, vérifié avec `crypto.timingSafeEqual` et expiration contrôlée côté serveur (secret dans une variable d'env serveur dédiée, p. ex. `RECOVERY_COOKIE_SECRET`). Option B : exiger en plus que la session soit récente (`last_sign_in_at` < 15 min via `getUser()`), ce qui n'est vrai qu'après le clic sur le lien. Après un changement de mot de passe, effacer le cookie (déjà fait) et révoquer les autres sessions (voir Y5).
- **Variantes** : aucune autre utilisation de `RECOVERY_COOKIE`.

### O2. Aucune limite de débit réellement efficace, et l'anti-bot (honeypot + `t`) est contournable à coût nul
- **Fichiers** : `src/lib/auth/rate-limit.ts:5-6` (Map en mémoire), `src/lib/checkout/rate-limit.ts:4`, `src/app/api/newsletter/route.ts:16` (3e copie), `src/lib/auth/bot-guard.ts:15-18`, `src/lib/checkout/schema.ts:67-72`, `src/lib/auth/http.ts:12-15` et `src/lib/checkout/rate-limit.ts:30-34`.
- **Confiance** : 9/10 · **VERIFIED** · empreinte `auth/rate-limit.ts:5:security`
- **Code en cause** : `const hits = new Map<string, number[]>();` (état par processus) ; `const t = Number(b.t); … if (elapsed < MIN_FILL_MS …) return "tooFast"` (horodatage fourni par le client) ; `const fwd = req.headers.get("x-forwarded-for"); (fwd?.split(",")[0] …)`.
- **Scénario d'exploit** :
  - En serverless chaque instance a sa Map vide, et chaque redéploiement/cold start remet les compteurs à zéro : la limite réelle est « N instances × limite ». Un attaquant parallélise et dépasse largement les 8 tentatives/10 min de `/api/auth/login` (credential stuffing, mots de passe faibles de clients), les 8 commandes/10 min de `/api/checkout` (amplifie R1), les 5 messages de `/api/contact`, les 8 inscriptions newsletter.
  - Le honeypot `website` et le délai `t` ne prouvent rien : un script met `website: ""` et `t: Date.now() - 3000`. Ce n'est qu'un filtre pour robots naïfs, pas une barrière.
  - Hors Vercel (hébergeur derrière un autre proxy), le premier élément de `x-forwarded-for` est falsifiable : une IP différente par requête contourne toute limite par IP. Si l'en-tête est absent, tous les visiteurs partagent le seau `"unknown"` : 8 commandes/10 min pour TOUT le site (auto-DoS).
  - Les mails (Supabase Auth : inscription, reset) coûtent du quota SMTP : `/api/auth/forgot` et `/api/auth/signup` peuvent être utilisés pour inonder des boîtes (limite par identifiant elle aussi en mémoire).
  - TENTATIVE : les appels `signInWithPassword`/`signUp` partent tous de l'IP de sortie du serveur ; les quotas par IP de GoTrue (≈30 connexions/5 min par IP par défaut) pourraient être épuisés par un flood et bloquer les connexions légitimes. À vérifier dans Supabase (Auth → Rate Limits).
- **Correctif** :
  1. Un seul limiteur persistant partagé : fonction SQL `rate_hit(p_key text, p_window interval, p_max int) returns boolean` sur une table `rate_limits(key, hits, window_start)` (service_role only, `revoke execute` comme les autres), ou Upstash/Vercel KV. Le brancher sur login, signup, forgot, checkout, contact, newsletter, reviews, track avec les mêmes clés qu'aujourd'hui. Supprimer les 3 implémentations dupliquées.
  2. Activer un CAPTCHA (Turnstile/hCaptcha) dans Supabase Auth et passer `captchaToken` dans `signInWithPassword`, `signUp`, `resetPasswordForEmail`, ainsi que sur checkout/contact. C'est le seul vrai remplaçant du honeypot.
  3. Sur Vercel, lire l'IP via `request.headers.get("x-vercel-forwarded-for")` / `x-real-ip` ; ne jamais faire confiance à `x-forwarded-for` hors plateforme qui l'écrase ; ne pas regrouper dans `"unknown"` (rejeter ou limiter plus bas).
- **Variantes** : 8 routes concernées (login, signup, forgot, checkout, reviews, contact, newsletter, orders/track) + me/profile et me/password (par utilisateur).

### O3. `profiles.phone` est un identifiant de connexion et de réinitialisation, mais il n'est ni unique ni vérifié
- **Fichiers** : `supabase/migrations/0001_core.sql:12` (`phone text not null default ''`, aucun index unique), `:33` (copié depuis `raw_user_meta_data`) ; `src/lib/auth/identify.ts:15-16` ; `src/app/api/me/profile/route.ts:29` ; `src/app/api/auth/signup/route.ts:38`.
- **Confiance** : 8/10 · **VERIFIED** · empreinte `identify.ts:15:security`
- **Code en cause** : `admin.from("profiles").select("id").eq("phone", normPhone(identifier)).limit(2)` puis `if (!data || data.length !== 1) return null;`
- **Scénario d'exploit** : n'importe qui peut s'inscrire (ou modifier son profil via `PATCH /api/me/profile`) avec le numéro d'une cliente, sans preuve de possession. Dès que deux profils partagent ce numéro, `resolveEmail` renvoie `null` : la victime ne peut plus se connecter ni réinitialiser son mot de passe par téléphone (déni de service ciblé, silencieux, la réponse reste « identifiants invalides »). En s'inscrivant AVANT la victime avec son numéro, l'attaquant « occupe » l'identifiant. Risque aggravé : la base de connaissances (`0002_seed_demo.sql:142`) promet que « les commandes passées se rattachent automatiquement au compte créé avec le même numéro ». Si cette fonction est écrite sur la base du téléphone non vérifié, c'est un IDOR complet (voir l'historique et les adresses de n'importe quel client). Le rattachement n'existe pas encore dans le code audité : il ne doit PAS être implémenté sur un numéro non vérifié.
- **Correctif** : soit retirer la connexion/réinitialisation par téléphone en J1 (e-mail seul, le Phone auth Supabase est de toute façon désactivé), soit ajouter `phone_verified boolean not null default false`, ne mettre `true` qu'après un code OTP (WhatsApp/SMS), restreindre `resolveEmail` à `phone_verified = true`, créer `create unique index profiles_phone_verified_uq on public.profiles(phone) where phone_verified`, et interdire à `authenticated` de modifier `phone_verified` (laisser hors du `grant update (…)` de `0001_core.sql:61`). Pour tout rattachement de commandes invité → compte : exiger l'e-mail confirmé identique à `orders.email`, jamais le téléphone seul.

## 🟡 MINEURES / durcissement

- **Y1. Pas de contrôle d'origine ni de Content-Type sur les POST/PATCH JSON** (`src/lib/auth/http.ts:18-27`, `src/app/api/checkout/route.ts:51-58`, `src/proxy.ts`). Le corps est lu avec `req.text()` puis `JSON.parse`, donc un formulaire cross-site en `text/plain` passe. Les cookies Supabase sont `SameSite=Lax` : les actions authentifiées (profil, mot de passe, logout) sont protégées, mais un « login CSRF » est possible (le navigateur de la victime est connecté au compte de l'attaquant et y laisse adresse/téléphone via le formulaire de commande préremplie). Correctif : dans `proxy.ts`, pour `/api/*` en POST/PATCH, refuser si `Sec-Fetch-Site` ∈ {`cross-site`} ou si `Origin` ≠ origine du site ; exiger `Content-Type: application/json`.
- **Y2. Aucun en-tête de sécurité** (`next.config.ts`). Ni CSP, ni `X-Frame-Options`/`frame-ancestors`, ni `Referrer-Policy`, ni `X-Content-Type-Options`. Clickjacking possible sur le checkout et le compte. Ajouter `headers()` (CSP adaptée à Next App Router : `script-src 'self' 'unsafe-inline'` pour RSC, + GA/Meta/Sentry quand ils arrivent en J3, `frame-ancestors 'none'`, `nosniff`, `strict-origin-when-cross-origin`). Aucun `dangerouslySetInnerHTML`/`innerHTML` trouvé dans `src` : bon point.
- **Y3. Inscription de tiers sans consentement**. `src/app/api/newsletter/route.ts:58` force `consent: true` sans double opt-in : n'importe qui peut abonner l'e-mail ou le numéro WhatsApp d'un tiers (spam, non-conformité consentement). Même logique à `checkout` : `customer.email` d'un tiers déclenchera les e-mails de confirmation de commande du chantier e-mail (bombardement d'une boîte). Prévoir un lien de confirmation pour la newsletter et une limite d'envois par destinataire côté module e-mail.
- **Y4. Avis : doublons possibles, aucune modération préalable, pas de lien avec un achat**. `src/app/api/reviews/route.ts:84-107` fait « lire puis insérer » ; sans index unique, deux requêtes simultanées créent deux avis du même utilisateur. Ajouter `create unique index reviews_user_product_uq on public.reviews(product_id, user_id) where user_id is not null and not seed;` et traiter le code `23505` comme `already_reviewed`. Les avis sont publiés immédiatement (`hidden:false`) et entrent dans la moyenne publique (`catalog/index.ts:146`) : un compte e-mail jetable suffit pour faire du review-bombing. Option : `hidden:true` par défaut jusqu'à modération, ou n'inclure dans la moyenne que les avis `verified`. De plus `reviews_read` (`0001_core.sql:297`) expose `user_id` à tout lecteur de la clé anon : restreindre les colonnes servies publiquement (vue sans `user_id`).
- **Y5. Les autres sessions survivent à un changement de mot de passe** (`src/app/api/me/password/route.ts:39`). Après `updateUser`, appeler `ctx.sb.auth.signOut({ scope: "others" })` pour qu'un jeton volé cesse de fonctionner.
- **Y6. Verrouillage et oracle de timing**. `loginSchema`/`idLimiter.hit(id.toLowerCase())` (`login/route.ts:25`) et `numberLimiter.hit(number)` (`orders/track/route.ts:28`) sont indexés sur une valeur choisie par l'attaquant : il peut bloquer la connexion d'une personne ou le suivi d'un numéro de commande (quand la limite devient réelle, voir O2). Prévoir un déverrouillage par e-mail ou clé composite `id|ip`. En connexion par téléphone, un numéro inconnu répond plus vite (aucun appel `signInWithPassword`) qu'un numéro connu : énumération de numéros par chronométrage, faible mais réelle ; un `withTimeout` constant ou une résolution factice atténue.
- **Y7. Configuration Supabase Auth à contrôler (hors code)** : « Confirm email » ACTIVÉ (sinon `signup` renvoie `signedIn` avec un e-mail non prouvé), « Secure password change » activé, liste d'URL de redirection limitée à `https://<domaine>/api/auth/callback/**` (pas de `localhost` ni de wildcard large en prod), protection contre mots de passe divulgués (HaveIBeenPwned) activée, longueur min ≥ 8 alignée sur le front. Définir `NEXT_PUBLIC_SITE_URL` en production : `siteOrigin` (`http.ts:30-34`) retombe sinon sur l'en-tête Host de la requête pour construire les liens des e-mails.
- **Y8. Données de démonstration à retirer avant la mise en prod** (`0002_seed_demo.sql`) : 48 avis fictifs insérés avec `verified=true, seed=true` s'affichent comme « achat vérifié » : risque de pratique commerciale trompeuse (à faire valider par Helena) ; `ledger`, `couriers` (numéros de téléphone), `product_costs` de démo restent admin-only par RLS mais n'ont rien à faire en base réelle. Le fichier fournit déjà les `delete` à lancer.
- **Y9. `zone` choisie par le client, non recoupée avec l'adresse** (`0001_core.sql:422-424`). Choisir `cotonou` avec une adresse de Parakou donne 1 000 F au lieu de 2 500 F et le franco dès 15 000 F. Impact financier faible : l'admin doit corriger la zone à la confirmation, ou le formulaire proposer une liste de communes (Cotonou, Calavi) plutôt qu'une saisie libre.
- **Y10. Fournisseur de paiement : repli silencieux sur le Mock** (`src/lib/payment/index.ts:46-49`). Sans clés FedaPay en production, `getPaymentProvider()` renvoie `{ pending: true }` : le client croit son paiement lancé et la commande se libère à l'expiration. En J3, échouer explicitement (`payment_unavailable`) quand `NODE_ENV === "production"` et que le fournisseur réel n'est pas configuré.

## ✅ Points conformes (vérifiés dans le code)

- **Escalade de rôle fermée sur les deux voies** : `handle_new_user` pose toujours `'client'` (`0001_core.sql:28-30`), `UPDATE` sur `profiles` limité aux 5 colonnes non sensibles (`:60-61`), trigger `profiles_guard_role` en garde-fou (`:43-53`), aucune politique `INSERT/DELETE` pour `authenticated`. Le rôle lu côté app vient de la table, jamais des metadata (`lib/auth/user.ts:47`).
- **RLS activée sur les 21 tables** (`:273-278`). `orders`/`order_items` : lecture limitée au propriétaire ou admin (`:307-310`), pas d'IDOR ; les invités (`user_id` nul) ne sont lisibles par personne via la clé anon (`null = null` n'est pas vrai). `product_costs`, `payments`, `ledger`, `couriers`, `messages`, `newsletter_subs`, `kb` : lecture admin seule ; `webhook_events` : aucune politique + `revoke all`. Le prix d'achat ne fuite pas : table séparée, jamais sélectionnée par l'API publique (`catalog/index.ts:143` liste explicite des colonnes).
- **Fonctions `SECURITY DEFINER`** : `search_path` figé, `revoke execute … from public, anon, authenticated` puis `grant … to service_role` pour `place_order`, `mark_paid`, `cancel_order`, `expire_stale_orders`, `_restock_order`, `handle_new_user` (`:487-497`) ; aucune n'est donc appelable avec la clé anon via RPC.
- **Prix, frais, total recalculés en base** ; le client n'envoie jamais de montant (`schema.ts:5`) ; `UUID` regex sur les ids ; stock décrémenté de façon atomique avec verrou de ligne (`:395,397`) ; ordre de verrouillage stable.
- **`mark_paid`** : idempotent (`webhook_events`), verrou `for update`, montant vérifié, commande annulée → `needs_refund`.
- **Anti-énumération** : login (message unique 401), signup (même réponse si l'e-mail existe, `:46`), forgot (réponse neutre), suivi de commande (`TRACK_NOT_FOUND` identique pour numéro inconnu et contact erroné), contact/newsletter (doublon = succès).
- **Clé `service_role`** : lue uniquement dans `lib/supabase/admin.ts` (`import "server-only"`) ; aucune variable `NEXT_PUBLIC_*` sensible ; `.env*` ignoré par git, `.env.example` sans secret. Identité via `getUser()` (jetons validés côté Supabase), jamais `getSession()`.
- **Injection** : aucun SQL construit à la main ; paramètres PostgREST/RPC ; `ids` filtrés par `^[A-Za-z0-9_-]{1,64}$` avant `.in()`/filtre ; redirections post-connexion via `safeInternalPath` (anti open-redirect) ; callback : `lang` validé, PKCE.
- **Réponses d'erreur** sans détail interne (codes seulement), `Cache-Control: no-store` sur les routes de session, journalisation limitée au code d'erreur.
- **Rendu** : aucun `dangerouslySetInnerHTML`/`innerHTML` dans `src`.
- `/api/me/orders` : filtre explicite `eq("user_id", ctx.userId)` EN PLUS de la RLS (évite que l'admin voie toutes les commandes).
