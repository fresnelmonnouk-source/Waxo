## Règles supplémentaires (back-office et serveur)
1. **Server actions** : fichier `actions.ts` avec `"use server"` en tête qui n'exporte QUE des fonctions `async` (les types/constantes vont dans un autre fichier sans `"use server"`). Chaque action : `assertAdmin()` d'abord, entrée validée par Zod, écriture via `createAdminClient()`, `revalidatePath` ciblé, retour `{ ok:true, … } | { ok:false, code, message }` (jamais de stack/erreur SQL brute côté client).
2. **Couche de données par domaine** : `src/lib/admin/data/<domaine>.ts` (lecture, avec repli démo) ; chaque agent n'écrit QUE dans ses domaines. Montants en XOF entiers (`fmtXof`). Le prix d'achat (`product_costs.cost`) n'est lu que par le back-office.
3. **Migrations SQL** : tu n'écris QUE ton fichier numéroté (liste ci-dessous) dans `supabase/migrations/`, **idempotent** (`if not exists`, `drop policy if exists`, `on conflict do nothing`), RLS activée sur toute nouvelle table, aucune écriture publique, fonctions `SECURITY DEFINER` avec `set search_path = public` et `revoke execute … from public, anon, authenticated; grant … to service_role`. Tu ne peux pas les exécuter (pas de base) : relis-les avec soin. Le schéma existant est dans `supabase/migrations/0001_core.sql` — ne le modifie pas.
4. **Tableaux de données** : pagination ou limite explicite (≤ 200 lignes par requête), recherche/filtre côté serveur ou sur liste bornée ; export CSV (UTF-8 avec BOM, séparateur `;`) neutralisant les cellules commençant par `= + - @` (injection de formule).
5. **Tests** : vitest pour toute logique pure (agrégations de stats, calculs de marge, validation, parsing), préfixe de fichier = ton domaine.
6. Toujours : `npx tsc --noEmit`, `npx eslint <tes fichiers>`, `npx vitest run`. Les erreurs `tsc` dans des fichiers d'AUTRES agents (en cours d'écriture) ne sont pas à toi : ignore-les. Pas de `next build/dev/start`, pas de git, pas de `npm i`.
7. Messages boutique : seuls E3 (`assistant`), G3 (`consent`), P4 (`packs`), F3 (`checkout`), I4 (nouveaux fichiers de messages `legal`… voir sa section) écrivent des messages ; FR et EN ont exactement les mêmes clés.

## Contrats d'intégration entre agents
- `sendOrderEmail(orderId, kind)` (`src/lib/email/index.ts`, stub actuel → F3 le remplace sans changer la signature) : appelé par **B2** à chaque changement de statut (`preparation|livraison|livree|annulee`) et par **F3** (confirmation/paid).
- Annulation de commande : **toujours** via la fonction SQL `cancel_order(uuid)` (restitue le stock) ; marquer payé manuellement (COD encaissé) = update `orders.paid=true,paid_at=now()` par B2.
- `AccountantPanel` (`@/components/admin/AccountantPanel`, sans props obligatoires) : A2 le monte dans la page carnet ; K l'implémente (lit lui-même ses données via `src/lib/admin/data/ledger` exportée par A2 : `getLedgerRows()`, signature `Promise<{id:string;date:string;cat:string;label:string;amount:number}[]>` — A2 doit l'exporter ainsi, K s'y adapte).
- Événement navigateur `waxo:assistant` (détail `{ text?: string }`, annulable) : émis par les boutons « Demander à l'assistant » (J1) ; **E3** écoute, ouvre le widget et appelle `preventDefault()`.
- Réglages publics : `settings` clés `brand`, `shipping`, `pay` (existantes) + `legal` (NOUVELLE, publique, ajoutée par **D2**/0004 : `{companyName, legalForm, ifu, rccm, address, phone, email, hostName, hostAddress, publicationDirector, apdpReceipt}` toutes chaînes, vides par défaut). **I4** les lit (via `src/lib/pages`) pour remplir les marqueurs « [à compléter] » des textes légaux ; D2 les édite. Aucune valeur inventée.
- Réglages lus par tous via `getSettings()` du catalogue (`src/lib/catalog`) ; D2 écrit dans `settings` (liste blanche de clés : `brand`, `shipping`, `pay`, `legal`, `flags`).
- Événements de suivi (G3 les définit dans `src/lib/tracking/events.ts` ; les autres agents n'appellent PAS le tracking directement en J3 — G3 branche lui-même les écouteurs/points d'appel dans ses fichiers et, au besoin, te demande un hook dans le rapport) : `view_item`, `add_to_cart`, `begin_checkout`, `purchase`, `search`, `generate_lead` (contact), `sign_up`.
